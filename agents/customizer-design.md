# The customizer round: an ingredient list the player edits

Status: DESIGN RESOLVED 2026-09-07, IMPLEMENTED in commits 3c5036e (language), 8b1570e (customize) and ade4735 (consumer); the report is in implementation-notes.md. This note is the design record for the round that closes the requirements gap between the charter as resolved (FkLua `agents/drafts/recipes-library-design.md`, 2026-08-31) and the library's stated value: a recipe customizer in the Mod Settings screen that lets a player override the ingredients and cost of any recipe or research the mod author enables it for. The charter's settings layer bound three things: enablement to a bool, crafting time to a double, and (through BetterBeltBalancer's port) ingredients and cost to a dropdown over author-written presets. Nothing in it let a player write an ingredient list. This round adds that, as a text setting holding a small language, and keeps every existing shape working.

The player-facing reference for the language is [docs/ingredient-list.md](../docs/ingredient-list.md). This note holds what that page must not: the measurements, the alternatives, the surface, the semantics the two halves must agree on, the harness, and the fold-in of BetterBeltBalancer's round-two friction.

## Decisions

1. **A mini language in one text setting per recipe**, not per-ingredient slot settings. The settings screen is a flat list per mod with no groups or conditional visibility (wiki, Tutorial:Mod_settings), so slots cost 2K+1 rows per recipe; one text field costs one row and can be validated with sentences the slots cannot give ("names two ingredients; a comma separates them").
2. **REVERSED: fallback with an ERROR line, never refusal, for anything the PLAYER controls; refusal stays for anything the AUTHOR declares.** This decision originally read "refusal, never fallback, for an edited text": a typed unknown name stopped the load naming the setting, the entry and the problem. What still holds is everything about the LANGUAGE: it names the problem rather than substituting a name, it suggests the case-folded or dash-folded name when that exists, and an UNTOUCHED text (the reserved word, after trimming) means the author's default with its presence ladders, so modpack tolerance is unchanged for players who never type.

   What was wrong was the CALLER. Measured on Factorio 2.0.77 (build 84539, mac-arm64, steam), a refusal over a typed value is a lock-out and not a diagnosis:

   - the engine rewrites `mod-settings.dat` on every successful load and on NO failed one (three consecutive failed runs left the file at one sha256), so nothing in a failed run edits the value that caused it, and the refusal is permanent until something outside the game changes the bytes;
   - the client shows `Error loading mods` with five buttons, `Disable listed mods`, `Disable all mods`, `Manage mods`, `Restart`, `Exit`, and a `Reset mod settings` checkbox. Walking `Manage mods` shows the Mods screen, which offers enable and disable and has NO Mod settings button, and its `Back` returns to the same error dialog rather than to the main menu. The Mod Settings screen is not reachable;
   - disabling and re-enabling the mod does not work: the engine does not drop a disabled mod's settings and the identical refusal returns, and a disabled mod's settings do not appear on the Mod Settings screen either, so the value cannot be pre-set before re-enabling;
   - the one escape measured is `Reset mod settings` plus `Disable listed mods`: six steps, every startup preference in the file lost, the mod disabled, and a restart needed.

   The same shape reaches a NaN stored in a double setting: the engine's own range check rejects a NaN for an int setting but not for a double, so it reaches the guest and would have refused there for ever.

   So: a player-controlled stored value the library cannot use behaves exactly as if the player had typed the reserved word (for a text) or as if the setting had been unreadable (for a number, which already took the declared default with a log line), and logs ONE error-level line. The line is `fkrecipes: ERROR: <reason>. The mod loaded with its own default instead; fix the text under Settings > Mod settings > Startup, then restart.`, with `number` in place of `text` for the two research numbers and the crafting time; `<reason>` is the sentence the refusal would have carried with the constant prefix `fkrecipes: ` trimmed off, because the line already opens with it. ERROR is uppercase deliberately: Factorio's `log()` has one channel and no severity (verified: `fk_log` maps to the global `log`, and there is no second channel and no level parameter), so the severity has to be in the text, and uppercase keeps the line out of a case-sensitive grep for the engine's own `Error` lines while a case-insensitive one still finds it.

   WHAT STILL REFUSES, and each is an author's declaration or a hand-edited file rather than a player's typing: every declaration check including a text setting's declared default and its round trip through the language, the merged-amount ceiling (only a ladder collapse reaches it, never a typed list, because the language refuses a duplicate in one), the packless unit, the cycle walk, the two cost-number and two crafting-time post-conditions over the DECLARED default the fallback lands on (which `validateSettings` refuses at the settings stage, so they answer only for a host test that calls `PlanData` on its own), and the unoffered stored dropdown value. That last one stays a refusal because the engine RESETS an out-of-list value to the default before any stage runs (measured), so the library never sees one through the game: the sentence is a hand-edited-file guard, not a player-facing path.

   THE PROPERTY IS NARROWER THAN "A PLAYER IS NEVER REFUSED", and saying it the wide way was wrong. What a fallback lands on is the AUTHOR's declaration, and that declaration is held to the checks it always was, so two of the refusals above are reachable by a player who typed: the packless unit, in a modpack where every declared science pack is absent, and the merged-amount ceiling, where the author's own ladders collapse two ingredients onto one name over 65535. MEASURED in both halves and byte-identically, over a plan whose declared packs all drop: a good typed list loads in 4 ops, a typo loads onto the declared packs and then refuses with `fkrecipes: the technology chain-forging has no science pack the game has; research takes at least one`. What is TRUE is that a value the player types never introduces a refusal a player who typed nothing would not also have hit: the same modpack refuses the same plan with the field untouched, and the typed value only changes what the log says on the way.

   THE REFUSAL CARRIES THE NOTE, because nothing else can. `resolve` accumulates its lines into `res.logs` and `PlanData` turns them into `Op`s only after every check has passed, so on a refused load the accumulated ERROR lines NEVER REACH THE HOST: a player whose text fell back and whose plan then refused would read a refusal about the mod's own declaration and never learn that their field was set aside, or that correcting it is the one thing they can change from inside the game. So every refusal raised after resolution carries ONE added sentence when at least one player-controlled value fell back: `. The stored value of <setting> could not be used, so the mod's own declaration applied; correcting it under Settings > Mod settings > Startup is what a player can change here.` It names the FIRST such setting in walk order, which is the same every run; it appears only when a fallback actually happened, so it is never advice about a field nobody touched; and both halves compose it in one place (`withFallbackNote` / `with_fallback_note`). **AMENDED by fix round 2's decision 2**: finding 14 of the consumer's second assessment measured that the client cannot reach the screen this sentence names, so the clause after the semicolon is gone and the composer is renamed `fallbackFact` / `fallback_fact`. What it adds is now the first clause alone, ending at `applied.`, and the four exits it decorates are unchanged.

   WHAT IS LEFT AFTER THE NOTE, recorded rather than papered over: the player is told what to change, but the load still stops when the author's declaration cannot produce a legal result in this mod set, and that refusal is one an untouched player hits too. Closing it would mean the library guessing a substitute for a declaration the author made, which is the rule the language exists to keep.

   ONE FIELD IS ONE LINE. A crafting-time setting is the only thing two declarations may share (`validateBindings` refuses a shared cost number and a shared text and says why), and a bad value in it logs ONE line however many recipes read it, naming the first recipe in declaration order: two lines would report one problem twice, and a gate counting ERROR lines would be counting declarations. The same walk-order list is what the note's first setting comes from.

   AND THE TWO SIDES SAY DIFFERENT SENTENCES ABOUT THE SAME RULE. A stored value is what the setting ANSWERED (`<setting> holds a research count below 1`); the value a fallback lands on is what the plan DECLARED (`<setting> declares a default research count below 1`). One wording over both would describe the setting's answer while talking about the declaration that replaced it. The ORDER the two rules are asked in lives in one place per number (`countFault`, `secondsFault`, `craftTimeFault`), so the sides cannot drift about what is wrong, only about how it is worded. A setting the World has no number for at all was never HOLDING anything, so it takes its `was not readable, so its default applies` line and no fallback line: only a value the setting actually answered with can fall back.
3. **Research cost is in scope** with the same language for the pack list plus an int setting for the count and a double for the seconds. SUPERSEDED IN PART by fix-round-2 decision 3: the seconds are an int setting now, and the two numbers mean 0 beside a research dropdown.
4. **Presets stay.** A dropdown of presets gains a `custom` value and the text applies only then. This is also the migration path from a dropdown a mod already ships: the dropdown keeps its legacy name and values, so every stored preference stays valid, and the customizer arrives beside it. Automatic pre-population of the text from the old choice is IMPOSSIBLE in the engine: the settings stage sees no stored values (measured, empty `data.raw`), nothing at the data stage can write a setting, and `settings.startup` is read only at the control stage (FkLua's abi note). What the library can do instead: compose the dropdown's description with each preset rendered in the language, so the player switching to `custom` can start from the preset they were on.

   **SUPERSEDED by fix-round-2 decision 3, 2026-09-13.** The half of this that held is the migration path and the composed description. The half that was wrong is the `custom` VALUE: the state "the player's text is in force" cannot live in a dropdown value, because one launch of a release that does not offer it destroys that state silently. The record is dated and stays as written; what the library does now is decision 3 below.
5. **Fluids** become expressible, both typed by a player and declared by an author (`FluidIngredient`), because a customizer that refuses `water` in a chemistry recipe is not a customizer. The engine's category rule (below) is enforced by the library with a sentence.
6. **The `World` interface grows additively from now on.** Round two of the pilot found that adding `EntityExists` broke every consumer's host fixture. Go gets `UnimplementedWorld`, a struct a fixture embeds whose methods panic naming the missing method; Rust gets default trait methods that panic the same way. New methods land there first and a fixture compiles until it actually needs them.

### Fix round 2 (2026-09-13)

The consumer's second migration assessment (BetterBeltBalancer `agents/migration-assessment-2.md` at commit `1caaf08`) measured a release-to-release property this round had not asked about, and it invalidates decision 4's mechanism. Decisions are numbered within this series and appended here as they resolve; earlier decisions above are marked SUPERSEDED in place rather than deleted, because the record is dated.

1. (reserved: the round's first decision landed with its own commit)
2. **A mod set never bricks the game either, and refusal is for what the author can see.** The rule is mechanical and keys on WHAT THE CHECK ASKS: a check that asks the `World` anything is ENVIRONMENTAL and degrades loudly; a check that reads only the declaration is an author bug and refuses by name. An environmental check stays a refusal only where degrading would overwrite another mod's prototype, hand the engine something it refuses anyway, or invent a value the author never declared; and one more the threat model rather than the rule supplies, a site the game cannot reach at all. It is deliberately NOT the wider claim "nothing an environment does can stop the load": that is decision 2 of the first series repeated one level up, and the list of surviving refusals below is what keeps it honest.

   The sites that STAY refusals, each with the exception it claims: the three `already exists in data.raw` sentences (degrading clobbers a stranger's prototype); the two named-prototype probes in the same walk, `place_result` and `ResultNamed` (a bare string with no declared ladder behind it, so there is nothing to degrade to); `a prerequisite cycle: ...` (emitting a cycle hands the engine a worse message, and the legitimate degrade, dropping the splice, is a design this round does not make); the six `CostOf(...)` sentences and the new "the unit of `<source>` holds a table this library cannot copy faithfully" for a pack list in neither engine form (the same, plus: a form this library cannot decode is not a licence to pass a name it never read); the packless refusal below; `readDropdown`'s `holds "<v>", which is not one of its values` (not reachable through the game, measured); and every declared-default post-condition, which is not environmental at all. Both halves carry a source-property test that holds every refusal site in the source to that table, counted.

   **WHAT DEGRADES, AND THE MEASUREMENT THAT FORCED IT.** Finding 13 of the consumer's second assessment: a preset research tier, and `CostOf`, copied a technology's unit wholesale and never asked whether its packs were usable, so a modpack that demotes a science pack from `tool` to `item` stopped the load on the DEFAULT setting with no `fkrecipes:` line at all. Measured for this round, headless on 2.0.77 build 84539, the engine's own two refusals: `Error while running setup for technology prototype "tprobe-t" (technology): Invalid research unit (iron-plate). Research unit(s) can only be tool type items at the moment.` for a pack that is an item and not a tool, and `Error in assignID: item with name 'water' does not exist.` for a name the game does not have at all, which names neither the technology nor the property. So the filter asks BOTH questions at once through the `ToolExists` probe the ladder already uses, decoding the copied `ingredients` in both engine forms (the short tuple and the long dictionary) and refusing a form it cannot decode. Each dropped pack logs `fkrecipes: <tech>: <name> is not a science pack this game has, so it is left out of the <source> cost`.

   A copied cost that keeps NO pack falls back to the author's own declared cost where there is one, which is a `CostBy` tier's `Fallback`, with one line: `fkrecipes: ERROR: <tech>: the <source> cost names no science pack this game has, so this mod's own declared cost applies instead`. It has its OWN composer and does not go through `playerFallback` / `player_fallback`: nothing was stored and nothing was typed, so there is no field on the settings screen to send anybody to. The prerequisite and the level cap stay, because the tier still chose that rung; only the price moved. Where there is no declared cost behind it, `CostOf` being the case (a bare string with no ladder), the refusal stays and now names what it tried: `fkrecipes: the technology <tech> has no science pack the game has; research takes at least one, and none of <names> is a science pack here`.

   **THE MERGE OVER A CEILING CLAMPS.** Two ladder collapses summing above 65535 items, or above 1e301 fluid, are capped at the ceiling with a line in the merge line's own voice rather than refused: which rungs the ladders landed on is a fact about the mod set. The DECLARED ceilings stay refusals, because an author writing 70000 of something reads only the declaration.

   **AND EACH OF THE THREE SAYS SO WHERE THE PLAYER LOOKS**, by decision 4's mechanism and with its own text. A clamped amount and a dropped science pack are arithmetic and presence a player cannot check anywhere; the resolve-or-drop ingredient LADDER gets no note, deliberately, because it is the library's advertised contract and the dropdown's own composed description already discloses it ("where one names something your mods do not have, the nearest thing they do have is used instead").

   **AND `withFallbackNote`'S ROUTE GOES, WHILE ITS FACT STAYS.** The sentence a refusal used to carry when a stored value had fallen back pointed the player at Settings > Mod settings > Startup, and finding 14 measured that the client cannot get there: the `Error loading mods` dialog offers Disable listed mods, Disable all mods, Manage mods, Restart, Exit and a Reset mod settings checkbox; `Manage mods` has no Mod settings button and its `Back` returns to the same dialog; `Restart` relaunches into an identical dialog over a file whose sha256 has not moved; and the one escape resets every startup preference and disables the mod. What that measurement condemns is the ROUTE and not the FACT the sentence carried with it, and the fact is still the only thing a refused load can say about a value the player typed, because the accumulated log ops never reach the host. So the composer is renamed rather than deleted (`fallbackFact` / `fallback_fact`), it decorates the same four post-resolution exits, and the whole of what it adds is `. The stored value of <setting> could not be used, so the mod's own declaration applied.`: no screen, no route, no advice. Every refusal otherwise names what the AUTHOR must change, which is what they already did. `res.fellBack` / `fell_back` has TWO readers and always did, which an earlier draft of this record got backwards: it is the per-setting dedupe that keeps ONE log line per field however many declarations read it, and its first element is the setting this sentence names. Decision 4's note is written unconditionally and does not read it.

3. **The text is the switch, and the `custom` dropdown value goes away.** A recipe's text setting applies whenever its stored value is not the reserved word `default`, and the dropdown beside it decides whenever it is. A research cost's three settings are the same rule per field: each of the three that is not at its declared default overrides the chosen tier, and the ones left at their default come from that tier. This library adds NO value to a dropdown and reserves none, so a dropdown's `allowed_values` is exactly what the author declared.

   **THE MEASUREMENT THAT FORCED IT**, from finding 3 of that assessment, on Factorio 2.0.77: a release that declares a dropdown RESETS a stored value its `allowed_values` does not list, and PERSISTS the reset, with no line in the log; every setting a release does NOT declare survives verbatim. So a state kept in a dropdown value is destroyed by one launch of an older release, on any rollback, in a modpack pinned to an older version, or on a second machine on the last public release; a state kept in a TEXT SETTING the older release does not declare is not touched at all. The settings screen also has no conditional visibility (measured in this note's own table), so no field can ever be hidden while the other decides and the pairing has to be said in prose.

   **WHAT THAT BUYS.** Adopting the customizer on a dropdown a mod already ships becomes an IDENTITY: the option list does not change, so no stored choice is reset and none changes meaning; the text setting is additive; a rollback loses nothing; and a return restores everything. That is the headline of docs/migration.md's section on it.

   **THE SURFACE THAT GOES WITH IT.** `IngredientChoices.Custom`/`CustomValue` and `CostChoices.Custom`/`CustomValue` are removed, and so is `CustomCost.Position`: a `CostBy` tier places the technology whether or not the settings beside it are in force, so the arm has no ladder of its own to carry. `RecipeSpec.IngredientsFrom` may now be declared beside `IngredientsBy`, and `TechSpec.CostFrom` beside `CostBy`; `Ingredients` and `Unit` stay exclusive with both. `CustomCost.Seconds` becomes an `IntSettingRef`, because a research time in whole seconds is a slider a player can land on.

   **ZERO IS THE RESERVED WORD OF A NUMBER.** Beside a `CostBy` dropdown each of the two number settings declares a default of 0, a minimum of 0 and a maximum, and 0 means the tier supplies that field; with no dropdown there is nothing to defer to, so each declares a minimum of at least 1 and a maximum. The tier's unit is taken WHOLE and written over field by field, so a `count_formula`, a `max_level` and any field this library has never heard of survive a player who moved one slider; the one wrinkle is that the engine prices a unit carrying both a count and a `count_formula` by the formula, so a count the player typed drops the formula and logs which setting took it.

   **NOTHING IS EVER EDITED AND IGNORED**, so the two `is edited, but ... is not on custom` lines are deleted with their producers. What replaces them is a clause on the line that records what was read: `; the <dropdown> choice <value> is set aside` for a recipe, where the override is total, and `; the <dropdown> choice <value> supplies what the settings leave at default` for a research cost, where it is per field. Two sentences, because they say different things.

   **THE SCREEN IS TOLD WHICH FIELD DECIDES**, which is the only thing left that a player could not otherwise know: a text setting's description gains a line naming the option above or below it, a dropdown with a text setting beside it gains the mirror of that line, and the two research numbers gain a description of their own stating their range and what 0 means. Which of `above` and `below` each uses is decided by comparing the two emitted `order` strings, so the sentence is true whatever order the author declared them in. The locale checker requires `[mod-setting-description]` on a research number for the same reason it requires one on a text setting.

   **AND THE PROTOTYPE SAYS IT TOO, WHICH IS WHY DECISION 4 BELOW LANDS IN THE SAME COMMIT.** The rule above is a rule and not a state: it says which field wins, and it cannot say which one is winning right now. A player who moves the dropdown while a non-default text sits under it gets nothing, and until decision 4 the only signal was a log line, which is not where a player looks. The two decisions ship together for that reason.

4. **A fallback says so where the player looks: the emitted prototype's own description.** When a stored setting value falls back, the RECIPE or TECHNOLOGY the setting is bound to gains one trailing line in its `localised_description`, naming the setting and pointing at the log. Author description present: `{"", "<description>", "\n<note>"}`; absent: `{"", "<note>"}`; no fallback: exactly what the prototype carried before, byte for byte. An ITEM never carries one, because the fallback is about what a recipe makes or what a technology costs.

   **ONE NOTE PER PROTOTYPE, THE FIRST IN WALK ORDER**, so the sentence is the same string every run; and a crafting-time setting two recipes read puts the note on BOTH of them, because two tooltips are two places a player looks even though one bad field is one log line. The note is recorded against the declaration as the fallback is noted, through a target the walk threads rather than a cursor it sets: a cursor left stale by one arm writes a note onto the previous declaration, and a parameter makes a caller that forgot it a compile error.

   **THE DESTROYED-INPUTS SENTENCE IS SCOPED TO WHAT DESTROYS**, which is a fallback that changes a recipe's INGREDIENT LIST and nothing else: the ingredient text's note and the ingredient text's ERROR line, the two readers of one constant. Changing a recipe costs a player something the engine will not give back, an assembling machine's input slots emptied of anything the new list does not use, up to eighty items destroyed rather than spilled, with no line anywhere (measured by the consumer's second assessment, finding 8), and that is worth saying before a player acts on it. **THE PROTOTYPE KIND IS NOT THE PREDICATE**, and scoping by kind was the first attempt: a recipe whose CRAFTING TIME fell back emits a byte-identical ingredient list and moves only `energy_required`, so a note chosen by kind tells that player, in the tooltip, that fixing the field will empty their assemblers, which it will not. A false sentence where a player looks is the grade this round exists to remove, and it contradicted the ERROR line beside it, which was already scoped to the ingredient text alone. So the caller that records a fallback says whether the ingredient list moved, through one named predicate both readers share (`movesIngredients` / `moves_ingredients`). The pack text and the two research numbers carry neither sentence, for the same reason: repricing a research destroys nothing.

   **ENGLISH LITERALS, NEVER A LOCALE KEY, AND THAT IS MEASURED.** On 2.0.77 an UNDEFINED locale key anywhere in a prototype's `localised_description` deletes the WHOLE description on the client, silently: no `Unknown key` marker, no empty line, the title and the ingredients still drawn, exit 0, and the engine's own dump holding every byte of the description. So no gate in this repository could see it happen. Wrapping the key as `{"?", {key}, "literal"}` rescues it, and that form is the answer for a SETTING's composed description; but the library has no localisation channel for prototype prose at all (`appendLocalised` wraps a consumer's own `Description` as a literal too), and inventing a key would make every consumer owe an entry whose absence deletes the sentence it was meant to carry. Every sentence this library composes onto a setting is already an English literal, and this follows the same precedent.

   **WHAT IS OWED.** No gate here can see a render: the dump carries the string whether or not it draws. The client render of this line at its longest, where it wraps in a real crafting tooltip and in the tech tree, is OWED and belongs to the same client round as the wrap questions already open below.

## Measured on Factorio 2.0.77 (build 84539, mac-arm64, steam), 2026-09-07

Every fact below came from a Lua-only probe mod run under `factorio -c CFG --mod-directory MODS --dump-data`, CFG a copy of the install's config.ini with `write-data` pointed at a private directory, MODS holding `fkrecipes-probe_0.0.1/{info.json,settings.lua,data.lua}` and a mod-list.json enabling base and the probe and disabling space-age, quality and elevated-rails. A refusal is the first `Error` line of the run's stdout; a success is exit 0 plus a written `script-output/data-raw-dump.json`. The probe bodies are one `data:extend` each, using `item(name)` = `{type="item", name=name, icon="__base__/graphics/icons/iron-plate.png", stack_size=10}`, `recipe(name, ingredients, category)` with `results={{type="item", name="iron-plate", amount=1}}`, and `tech(name, unit)` with the automation-1 icon at size 256.

## The language, and why it looks this way

The reference is docs/ingredient-list.md. The choices:

- **Amount first, then name, commas between entries.** It reads like a recipe card, needs no operator, and a missing amount means 1. The forms a Factorio player types from habit (`2x iron-plate`, `iron-plate x2`, `iron-plate*2`, `iron-plate 2`) are accepted because they are unambiguous: a number never looks like a name (a digits-only name is reachable only through its tag), and `x` is an operator only when it stands alone or is glued to a number. `*` and `×` cannot appear in a name and always split.
- **No `:` or `=` amount separators.** They collide with the rich-text tag and with any future `key=value` clause. A player who types `iron-plate:2` gets a sentence quoting the character and showing the canonical form.
- **The game's own rich text is the tag form.** `[item=name]` and `[fluid=name]` are what shift-clicking produces in a text field, they disambiguate an item from a fluid of the same name, and they reach names that look like amounts. A `,quality=` parameter is refused with the plain form to write instead.
- **`none` is the explicit empty list**, so a free recipe is something a player says on purpose. An empty text is refused with the format to write. Research refuses `none`.
- **Fluid before item is never guessed.** Untagged names resolve item types first (the 21 `defines.prototypes.item` types the library already probes), then `fluid`. Packs resolve `tool` only, and an item that is not a tool gets its own sentence, because that is the engine's rule and its own message does not name the setting.
- **Every message quotes the entry as typed and numbers it from 1.** Character offsets are fragile across UTF-8 handling in two languages; an entry number plus the quoted text is exact and stable.
- **Entry diagnosis order is fixed** so both halves say the same thing for a malformed entry: a character outside the syntax (first one, quoted) or a minus-number, then no name, then two amounts, then two names, then more than one sign, then a sign with no amount, then a sign not between amount and name, then an amount of zero, then resolution, then the kind rules (a fluid in the crafting category, a fraction on an item, the item ceiling, the fluid ceiling), then duplicates across entries (first pair in order: the second occurrence with the lowest index, paired with its earliest partner). Across the whole list, the bracket-aware comma split runs first, the last entry is dropped when it is empty and more than one came back (that is the tolerated trailing comma), then every empty entry is reported positionally BEFORE the `none` rule, so `none, , 2 iron-plate` and `none,,` both report entry 2 empty and `none,` is the empty list. In a pack list a `[fluid=...]` tag is looked up as a fluid whatever the name is: an existing fluid is refused as a fluid, anything else is "no fluid is named", and it never resolves to a pack. The corpus pins each of these because the two implementers, aligning to each other's intermediate trees, first landed on opposite answers.
- **Rendering is the inverse.** The declared default and the log line render as `<amount> <name>` joined by `, `; fluids as `<amount> [fluid=<name>]`; an item whose plain name would not lex back as one plain name (an amount shape, a sign shape, the words `none` and `default`) in its `[item=...]` tag; integers plain; fluid amounts as the fewest significant digits that read back to the same double, never in exponent form. Rendering then parsing a rendered list is an identity, and both suites test it as a property over their fixtures.
- **The decimal rule, because the obvious one was wrong twice.** Go's shortest-round-trip printer and Rust's `Display` break the last digit differently on exact ties (the transcript formatter met this first; the code review of this commit found it again in the renderer, with 129 divergences in 204,105 doubles, the smallest at 1.0000076293945312). The renderer therefore does not use either. For p from 0 to 16 it formats v in scientific form with p digits after the leading digit, correctly rounded at that fixed precision (Go `strconv.FormatFloat(v, 'e', p, 64)`, Rust `format!("{:.*e}", p, v)`; both are exact at a fixed precision, which the transcript formatter already relies on at p = 16), takes the mantissa digits D and the exponent, and considers the three candidates D minus one in the last digit, D, D plus one (only those that need no borrow or carry). A candidate qualifies when its scientific form parses back to exactly v. None qualifying: next p. Otherwise, in ascending order, the first qualifying candidate whose last digit is even; if none is even, D when it qualifies, else the first qualifying one. That makes the choice independent of how either platform rounds an exact tie. The chosen digits are then laid out in fixed notation from the exponent, with no trailing zeros in a fraction and no dot when the fraction is empty. The same routine renders the seconds in the research log line. The corpus pins two exact ties (1.00000762939453125 and 1059438285926254.25) beside the ordinary values.
- **Two lexical corrections from the same review.** The thousands shape requires a nonzero integer part (`^[0-9]*[1-9][0-9]*\.000$`), so `0.000` is an amount of zero and gets the "more than 0" sentence rather than advice about a thousand. A sign in front of an exponent number (`-1e3`) is "is not an amount" like `-2` and `1e3`, not a name. And the order of the trailing comma against the bracket rule: split on commas outside brackets FIRST, then drop the last entry when it is empty and more than one came back; a comma at the end of an unclosed tag therefore stays inside the tag and is quoted back (`[item=iron-plate,` is one entry).

## Semantics both halves must share

Plan time (host-testable, refused before any op):

- The exclusivity rules above, with sentences naming the recipe or technology and the two fields.
- A `Custom` arm requires the dropdown's values to contain `custom` exactly once and the `Choices` to cover every other value, in order, exactly once. A text setting is bound exactly once (one recipe or one technology); an unbound one is refused as a declaration mistake. A count or seconds setting read as a research number is read by exactly one declaration too (the follow-up round, item 7c: otherwise the ignored-number line would name a setting something else is using), while a crafting-time setting may still serve two recipes.
- `CustomCost.Count` and `Seconds` bounds as above, checked on the DECLARED spec so the engine's own reset rule (out-of-range resets to the default) keeps every readable value legal.
- A declared fluid ingredient in a recipe whose `Category` is empty or `crafting` is refused with the measured rule; a player-typed one gets the same sentence at the data stage, inside a fallback line (decision 2).
- The rendered default of every text setting parses back to the same list.
- Handles validated as every handle is (zero, wrong Lib).

Settings stage:

- A text setting emits a `string-setting` with `default_value` = the rendered default, `auto_trim = true`, no `allowed_values`, no `allow_blank`, order from declaration order (or the legacy order), and no inline name or description: both come from the consumer's locale, and the checker treats the description as REQUIRED for a text setting because the library composes four things under it (see the client round below).
- A dropdown that has a `Custom` arm emits `localised_description = {"", {"mod-setting-description.<full>"}, <preset 1>, ... <preset N>}` in choice order, so the player can see what each preset means in the language. A preset is a NESTED table and never a flat string: an ingredient preset is `{"", "\n", {"string-mod-setting.<full>-<value>"}, "\n  type: <rendered list>"}` and a cost preset is the same head with `": cost of ", {"technology-name.<first source>"}` behind it (the two preset shapes are written out under Orderings below). The consumer's description key is therefore required too. The ingredient preset's `": "` separator became the second line in the client round below; the preset was a nested table before that change and after it.

Data stage:

- The text is read through `StartupSetting`; unreadable takes the declared default with the existing log line; a non-string takes the declared default too, with the fallback line carrying `<setting> is not text` (decision 2: the engine resets a wrong-typed stored value before any stage runs, so it is a hand-edited file, and the line says so without stopping the game).
- Trimmed text equal to the rendered default: the author's declared list with its ladders, exactly the pre-existing path, and no log line.
- Otherwise: parse and resolve per the reference. On the first problem the language's sentence goes into ONE fallback line and the declared default applies with its ladders, exactly as the reserved word does (decision 2); otherwise the list is emitted in the typed order and one line records it: `fkrecipes: <emitted recipe name> takes its ingredients from <setting>: <canonical>`.
- Under `IngredientChoices.Custom`: dropdown value `custom` selects the text path; any preset value selects that preset as today. A stored value that is none of the dropdown's values (unreachable through the engine, which resets it, but reachable through a hand-edited file) is REFUSED: `fkrecipes: <dropdown> holds "<value>", which is not one of its values`. This closes the pilot's "unknown option yields a free recipe with no log line".
- Research under `Custom` or `CostFrom`: count and seconds always come from their settings; an untouched pack text means the declared default packs, presence-probed as `tool` and refused by name if absent; an edited one is parsed. The unit is `{count, time, ingredients={{name, amount}, ...}}` in the short tuple form. Under `CostChoices.Custom` the prerequisite is the first technology in `Position` that exists, or none with a log line, in the Fallback shape. The log line: `fkrecipes: <technology> takes its research cost from <packs setting>: count <n>, time <seconds>, packs <canonical>`.
- A fluid ingredient emits `{type="fluid", name=<name>, amount=<f64>}`; an item keeps `{type="item", name, amount=<int>}`.

Every figure in this paragraph is the pilot's, out of `agents/fkrecipes-migration.md` in the BetterBeltBalancer checkout, taken from the engine's own settings dump with that mod's locale substituted rather than off a screen. The sentence claiming that shift-clicking an item inserts rich text into a settings text field was removed from the reference: startup settings are edited from the main menu, where no inventory exists.

## The client round: what a real screen said, and the three lines it bought (2026-09-09)

The pilot ran a real client against a migrated consumer on Factorio 2.0.77 and looked at the Mod Settings screen the composition produces. It answered three of the open claims above and found three defects, and this section is the record of both and of the shape they changed.

What the screen does. THE TOOLTIP RENDERS WHOLE: the composed description's `\n` are line breaks and all seven lines of a recipe setting's description were readable and unclipped, which is what makes the description a place the library can say things. THE SEVEN IS THAT DAY'S SHAPE AND NOT A CEILING, which is the one thing to carry out of this section rather than the number: it is the pilot's six presets plus its own entry with each preset on ONE line, and the same dropdown composes 13 under the two-line shape the first defect below bought. The ceilings are the parameter count and the nesting depth, and a line count reaches neither; the claims paragraph above carries the re-measurement and the wrap question that stands in its place. THE CLOSED DROPDOWN'S LABEL IS TRUNCATED AT ABOUT 37 CHARACTERS (`Default: 4 iron plates, 2 gears, 2 tra`), and five of the seven options in the open list were truncated with an ellipsis. THE FIELD HAS NO LENGTH LIMIT OF ITS OWN: the `string-setting` prototype this library emits declares no maximum-length key at all, so the engine would store 98000 characters and the 2000-character ceiling is the LIBRARY's; measured at exactly 2000 on the client too (1999 and 2000 load, 2001 refuses).

The three defects, and the answer to each.

| Defect | Answer |
|---|---|
| The composed tooltip printed each preset as `<label>: <internal list>`, one run of text in two vocabularies separated only by `": "`. The first half is the consumer's display prose and pasting it into the field beside it is REFUSED; the second half is what the field takes; nothing said which was which, and the truncated label a player actually sees in the closed widget shows only the half that refuses | An ingredient preset line becomes `{"", "\n", {"string-mod-setting.<full>-<value>"}, "\n  type: <rendered list>"}`. Three parameters, as before, so no parameter budget is spent: the change is `": "` becoming `"\n  type: "`. A COST preset keeps its `": cost of ", {"technology-name.<first source>"}` tail, because a localised label followed by a localised technology name is ONE vocabulary and there is nothing in it to copy |
| The 2000-character ceiling and the internal-name format appeared nowhere a player looks | The text setting's description gains `"\nWrite internal names, as the default line above does, in at most <maxListChars> characters."` after the default line. The number is the language's own constant in both halves, never a digit typed into the sentence, so the limit the player is told and the limit the parser enforces cannot drift |
| Nothing said what happens to a text the library cannot use | And it gains `"\nA text this mod cannot use is set aside and that default applies instead; the reason is in the log, or in the load error if the load stops anyway."` The text is set aside for the declared list (decision 2), so a player whose text went unused is left looking at a settings screen that still holds it: this is the only warning available before the fact. IT PROMISES THE NARROW CLAIM AND NOT A LOAD, because the narrow claim is the only one true: the declared list is held to every rule it always was, so a modpack in which that declaration cannot produce a legal result still stops the load, and on a refused load no log op reaches the host at all, so the load error is the only place the reason can be. An earlier draft of this line said the mod loads and the log says why, and both halves of it fail together in exactly that case |

WHY THE SECOND LINE IS HONEST AT 37 CHARACTERS, which is the objection this shape has to answer. The truncation is of the dropdown's own LABEL, in the CLOSED widget, and that label is the consumer's string: nothing this library composes can lengthen or shorten it. The composed description is the TOOLTIP, and the client renders the tooltip whole. Under the old shape the tooltip line was `<label>: <internal list>`, one run of text whose two halves were separated only by `": "`, so nothing marked where the copyable half began and a truncated label showed a player only the half that refuses. Under the new shape there is no composite line to truncate at all, which is the part of the old argument that survives: the copyable half opens its own line under the label, indented by two spaces, and each preset's copyable half is a line of its own, so the tooltip carries one `type:` line PER PRESET, up to nineteen of them flat. What a player looks for is therefore a shape rather than a unique line, and what the change bought is that no line mixes the two vocabularies. The fix is not "make the label fit"; it is "stop putting the two vocabularies in one line", and that is a change to the line the library owns rather than to the string it does not.

IT IS MITIGATION AND NOT ELIMINATION, and the argument above should not be read as total. A player who selects the whole composed line and retypes it, `  type:` and all, gets the same message class the old defect produced, measured against the parser on the head of this change: `fkrecipes: mymod-parts, entry 1 ("type: 4 iron-plate"): ":" has no place here; names use the letters a to z, digits, - and _, and an amount is plain digits, as in "2 iron-plate"` (the two leading spaces are trimmed before the entry is quoted). What the two-line shape removes is the case where the label and the list are ONE run of text with nothing marking the boundary; what it leaves is a player who copies more than the line offers, answered by a refusal that quotes the offending character back at them.

A KNOWN OVERLAP WITH THE CONSUMER'S OWN ENTRY, recorded rather than left to be discovered. The pilot's `[mod-setting-description]` for its ingredients setting already reads "Write the amount, then the item's internal name, and separate ingredients with commas: 2 iron-plate, 1 splitter. Internal names are the ones the game uses in its own data and in rich text, not the names shown on screen", so for THAT consumer the format half of the new line says a second time what the entry above it already says, with a second example. The two halves of the measured gap were the LIMIT and the FALLBACK, neither of which that entry mentions and neither of which an author can be expected to know. The format half is kept anyway because a consumer who writes nothing gets it, and because the sentence it duplicates is the one an author is most likely to leave out; the cost is a duplicated clause on a well-written entry, which is the cheaper of the two failures.

THE CEILINGS WERE RE-MEASURED before the shape was fixed, out of FkLua's data-stage probe (`agents/datastage.md`, rows `locstring-params-20`/`-21`, `locstring-nest-19`/`-20`, `locstring-nested-groups`), which takes them at the SETTINGS stage on a `string-setting`'s `localised_description`, the very prototype field this composition writes: 20 parameters load and 21 refuses, and 19 parameters plus a nested group of 20 load. THE NESTING FIGURE IN THAT PROBE'S ROW NAMES WAS READ AS A TABLE COUNT AND IT IS A LEVEL COUNT: the limit is 20 LEVELS and the 21st refuses, so the corrected reading is in the decisions table row above and the earlier "19 nested tables" here and below is wrong. Measured out of the engine's own `mod-settings-dump.json` on 2.0.77, over the example guest: a TEXT setting's description is 5 parameters at one level and 2 tables deep (4 before the switch line this round added); an INGREDIENT dropdown's is 3 parameters at the top with 3 in each preset line, 3 tables deep; a COST dropdown's is 3 at the top with 4 in each preset line, 3 tables deep. The text setting therefore spends 5 of 20 and 2 of 20, and the preset shapes are unchanged in both counts, because the change is inside a string.

THE LOCALE CHECKER GAINS THE DRIFT GUARD, not an author finding. `CheckLocale` / `check_locale` reports `the library composes no line about the format and the length limit onto a text setting's description; a text setting's description carries one, so this is a defect in fkrecipes and not in this locale file` and its twin `... no line about what happens to a text this mod cannot use ...`. ONCE PER REPORT AND FIRST IN IT, not once per text setting: what the rule inspects does not vary with the setting (both lines are constants, and the only per-setting part of a text description is the consumer's key, which the rule does not read), so run inside the per-setting loop it turned ONE library defect into five findings on the example guest and at fifty text settings the two sentences alone would have filled `localeFindingCap` and pushed every author finding out. It is emitted ahead of the parse findings and of every rule about the author's file, which is also how it survives the cap: the cap keeps the first hundred findings and replaces the tail with a count, so a rule that goes first cannot be dropped by a file that produces a thousand of its own. A plan with no text setting composes no text description and the guard has nothing to inspect, so it is silent there; the composition it is handed is the FIRST text setting's in declaration order. Nothing a consumer can type produces either: the library composes both, so a report means the library shipped a description missing a line it owes. It lives in the checker because the composition has no other reader that runs on a host, and it is the only guard that catches the loss without a Factorio binary.

WHAT THE GUARD IS HANDED IS THE COMPOSITION WITH THE DECLARED LIST LEFT OUT, and that is the one deviation from "check what is emitted". Rendering the list is the only part of the composition that reaches the language, and it is also the only part that dereferences an item handle; the checker validates nothing by design, so a plan the planners would refuse must not panic in it. With the list left out neither the language nor the item table is touched and the two lines under test are still there to see. THE SENTENCES THEMSELVES LINK NO LANGUAGE, AND THEY DO COST BYTES, which are two claims and not one. The ceiling is a CONSTANT (`maxListChars`, Rust `MAX_TEXT`, made `pub(crate)` for this), and naming a constant is not a code reference, so the source-property tests in both halves are unaffected and a plan with no text setting still links no parser and no renderer. The bytes are a separate measurement and they are not zero: the sentences ship in every consumer, text setting or none, because the composition that holds them is linked either way. Measured over the whole client round, HEAD against the round, with the harness's own build flags and the fklua the mirror builds, packaging each guest as the size table above does: `go/examples/notext` 2,706,758 to 2,710,197 bytes of `fk_data_module.lua` (+3,439, +92 lines; wasm 715,185 to 716,624) and `rust/examples/notext` 2,291,692 to 2,293,724 (+2,032, +30 lines; wasm 149,409 to 149,774), with no language string linked in either. The declaring guests move by more, because their descriptions carry the sentences per setting as well: `go/examples/datastage` 3,843,914 to 3,857,652 (+13,738) and `rust/examples/datastage` 3,328,741 to 3,330,780 (+2,039). That the numbers are small is the point; that they are zero is not the claim, and the round's cost is the whole delta above rather than the sentences weighed on their own. The number that holds the ceiling honest is a SOURCE property rather than a value test, because a typed 2000 and the constant render the same bytes while the ceiling happens to be 2000: `TestTheCeilingIsNeverTypedIntoAMessage` and `the_ceiling_is_never_typed_into_a_message` forbid the ceiling's own decimal rendering in every string literal either half builds a message out of. The composition function is the single reader of both sentences, which is what makes deleting a line from it a finding rather than a silent loss.

THE CONSUMER'S OWN DESCRIPTION ENTRY IS FOR SOMETHING ELSE NOW, and the missing-entry sentence says so: `the setting <full> has no [mod-setting-description] entry, and a text setting needs one to say what the setting is for; the library composes the format, the limits and the fallback onto it`. It used to say the entry was where the format is explained, which stopped being true the moment the library started explaining it.

TWO THINGS AN AUTHOR NEEDS THAT THIS LIBRARY SAYS NOTHING ABOUT IN CODE, folded into migration.md rather than into a refusal, because both are the consumer's or the engine's. A stored dropdown value an older release does not offer is reset to that release's default before any stage runs, with NO log line, and the reset is persisted (measured on the pilot: head with `custom` chosen and a text edited, one launch of the last published release, then back to head; both dropdowns reset and written back, the four settings that release does not declare untouched). The typed text SURVIVES, which is what makes it dangerous: the field still shows the player's recipe, so the screen looks like nothing was lost. And a `Custom` cost arm moves the technology in the tree even when all three numbers are untouched: `prerequisites` becomes the ladder's first existing entry rather than the source's, which is a code fact because a custom cost has no source technology to take a position from. The unit was byte-identical to the source's on the pilot, and that half is CONTINGENT: the pilot's `CustomCost` settings happen to declare the source technology's own count, seconds and packs as their defaults, and nothing in this library ties a Custom arm's declared defaults to any source's unit, so an author whose defaults differ moves the cost too. Neither can be said on the settings screen, so both belong in the author's changelog, and migration.md carries the condition with the claim.
